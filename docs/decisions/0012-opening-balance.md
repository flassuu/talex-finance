# ADR 0012 — Opening balance as a system entry

- **Status:** Accepted
- **Date:** 2026-11-05
- **Deciders:** project owner
- **Related questions:** Q-027 (resolved by this ADR)

## Context

D-008 says balances are computed from initial balances and financial entries. The
product owner wants to enter the amount already on an account when it is created:
a card with 500 € should start at 500 €, not at zero plus a fake income entry.

The ledger rule is that an account balance is the sum of its entries. If the
opening amount is stored as a separate field on the account, the balance has two
sources and can drift. If it is stored as an ordinary income entry, reports would
treat existing money as new income.

## Decision

An account can be created with an optional starting balance.

- The account creation form has a "starting balance" field, default 0, in the
  account's currency.
- A non-zero starting balance is stored as a system entry of type `opening`,
  dated on the account's opening date.
- The opening entry has no category, tags, payee or split lines. Its description
  is generated by the app and localized.
- Only one opening entry exists per account. A zero starting balance creates no
  entry, because zero entries are invalid.
- The opening entry is included in the account balance and in net-worth history
  from its date.
- It is excluded from income, expenses, budgets, savings-rate calculations and
  the works/idle/lost metrics.
- The opening amount can be edited while the account exists. Deleting it is part
  of deleting the account, not a separate action.
- Imported accounts may carry an opening balance; imported transactions remain
  separate entries dated as in the file.

## Alternatives considered

| Alternative | Why it was not chosen |
|---|---|
| Store the starting balance as an account field | The balance would have two sources (field plus entries) and could drift; the ledger rule would no longer hold. |
| Record the starting balance as income | It misclassifies existing money as new income and distorts every report. |
| Start every account at zero and require a manual adjustment | Extra work and easy to forget; the account never matches reality until the user compensates. |
| Create a zero opening entry | Zero amounts are invalid and add noise. |

## Consequences

- **Positive:** the account starts at the real amount; the balance stays a sum of
  entries; reports do not mistake existing money for income; the opening amount is
  auditable.
- **Negative:** one more system entry type; the account creation flow writes two
  rows atomically; deleting an account must delete its opening entry too.
- **Follow-up:** `docs/technical/ledger.md` defines the `opening` type and
  balance; `docs/technical/database.md` records the entry; import and backup must
  preserve it.
- **Resolved question:** Q-027 is closed as "a system opening entry created from
  the starting-balance field".

## Review

Revisit if users need multiple balance corrections over time. That would call for
an explicit adjustment entry type, not a second opening entry.
